= Architecture
:experimental:
:toc: left
:toclevels: 2

Skrivro is a Tauri 2 application: a Rust binary that hosts a system WebView, with the actual editor and preview UI implemented as a small TypeScript / HTML / CSS frontend.
The Rust side handles filesystem I/O, OS integration, config parsing, and a few platform-specific things (macOS menu, Linux GTK app-id workaround). The frontend handles everything the user sees.

This doc describes how the pieces fit together for anyone reading or modifying the code.

The WebView is platform-provided:

* Linux: WebKitGTK 4.1
* macOS: WKWebView (system WebKit)
* Windows: WebView2 (Chromium-based)

Skrivro doesn't bundle a browser engine.
That's why the binary is ~15-20 MB on Linux instead of the ~150-300 MB an Electron app would be.

== Rust side (`src-tauri/`)

The Rust source is intentionally monolithic: almost everything lives in `src-tauri/src/lib.rs`.
For a project of this size and feature surface, splitting `lib.rs` into many small modules adds navigation overhead without making the code easier to reason about.
The single file uses ASCII-art section headers to delineate logical groupings.

`src-tauri/src/main.rs` is a one-line entry point that calls `skrivro_lib::run()`.

Major sections of `lib.rs`:

[cols="1,3", options="header"]
|===
| Section | What it does

| Pending opens
| `Mutex<Vec<String>>` for files that arrive via OS-dispatched open events before the frontend's listener is registered. Drained at init time via `take_pending_opens`.

| Config types and parser
| `SkrivroConfig` struct (with `#[serde(rename_all = "camelCase")]` so the JS side sees camelCase keys), `ThemeColors` struct, `parse_skrivro_config` and `parse_theme_file` parsers, and the `normalize_length` helper for length-typed values.

| Theme loading
| `load_theme`: checks user-supplied `<app_config_dir>/themes/<name>.theme` first, falls back to bundled themes embedded via `include_str!()` at compile time.

| Tauri commands
| `#[tauri::command]` handlers exposed to the frontend: `get_launch_info`, `get_config`, `get_session_state`, `set_session_state`, `take_pending_opens`.

| `run()` function
| Builder setup, plugin registration, window creation, platform-conditional code (macOS Cocoa chrome hiding, Linux glib::set_prgname).
|===

`Cargo.toml` declares the Tauri version, the `tauri-plugin-*` crates (dialog, fs, shell, single-instance, window-state), and platform-conditional dependencies (`objc2`, `objc2-app-kit`, `objc2-foundation` on macOS for direct Cocoa calls, and `webkit2gtk`, `glib` on Linux for the GTK context-menu filter and the prgname workaround).

== Frontend (`src/`)

The frontend is structured around feature-based modules.
Each module owns its DOM references, its state, and its exports.

[cols="1,3", options="header"]
|===
| Module | Responsibility

| `main.ts`
| Top-level bootstrap. Imports and wires every other module. Fetches launch info and config from Rust. Constructs the EditorView. Registers the global keyboard handler. Sets up file-association event listeners (`skrivro:open-file`, `onDragDropEvent`, `onCloseRequested`).

| `editor.ts`
| CodeMirror 6 setup. Constructs the `EditorView`, configures language compartments (asciidoc / markdown / text), exposes `getDoc` / `setDoc` and the live `editorView` binding. Owns the language and Vim-mode CM6 extensions.

| `preview.ts`
| Preview-pane orchestration. Calls the active renderer, injects HTML into the DOM, manages scroll-sync state, handles external link delegation (open in system browser via Tauri shell plugin), gates external image loading.

| `renderer.ts`
| Format-keyed dispatch and worker coordination. The `Renderer` interface returns `{ html, buildBlockMap, translateEditorLine }`. The AsciiDoc path wraps `@asciidoctor/core` plus the include preprocessor, the Markdown path wraps `markdown-it` with the GFM-alert, task-list, and emoji rules, and the text path escapes and wraps in `<pre>`. The heavy conversion runs in `render-worker.ts` (see below) so the main thread stays responsive.

| `io.ts`
| File operations: `openFile`, `saveFile`, `saveFileAs`, `newFile`, `loadFileFromPath`, `confirmDiscard`. The `currentBuffer` state object (path, name, format, dirty). Vim Ex command registration. Autosave debouncer. Session state read/write.

| `ui.ts`
| DOM-level UI: status bar updates (mode pill, dirty indicator, cursor position, word count), display mode switching, top-bar / status-bar / gutter toggles, help dialog, confirm dialog, `applyUserConfig` for translating Rust config values into CSS custom properties.

| `menu.ts`
| macOS menu bar. Custom items for Quit / Close / Minimize that route through `onCloseRequested` for dirty-buffer protection. `installMenu()` is called only on Mac at init time.

| `i18n.ts`
| Translation table (`STRINGS_SV`) and the `tr()` helper. `lang` is resolved once at module load from `window.__SKRIVRO_LANG__` (set by an inline script that reads the Rust config override or falls back to `navigator.language`).

| `prefs.ts`
| LocalStorage-backed UI prefs (Vim mode, gutter visibility, status bar visibility, display mode, etc.). Distinct from `config.ts`: prefs are per-machine UI state, while config is per-user customization from the config file.

| `config.ts`
| Type definitions matching Rust struct shapes (`SkrivroConfig`, `ThemeColors`, `LaunchInfo`, `SessionState`). Live binding `userConfig` populated from Rust at init time.

| `render-worker.ts`
| The rendering Web Worker. Runs the heavy parse-and-convert (Asciidoctor for AsciiDoc, markdown-it plus the GFM rules for Markdown) off the main thread, so typing stays responsive on large documents. `renderer.ts` posts source to it and gets HTML plus the block map back.

| `spellcheck/`
| The spellcheck subsystem: `index.ts` wires it into CodeMirror, `spellcheck-worker.ts` runs the nspell check off-thread, `custom-words.ts` holds the personal dictionary, and `spell-menu.ts` builds the right-click suggestions menu.

| `perf.ts`
| Render-timing instrumentation. Emits `[perf]` lines to the dev-build console for spotting slow renders.
|===

`index.html` is the single HTML entry point.
It contains the static DOM structure (titlebar, editor host, preview container, status bar, help dialog, confirm dialog) and small inline `<script>` blocks at the end of `<body>` for FOUC prevention (theme color resolution + language detection before the main module loads).

`styles.css` holds all CSS: both the layout / chrome and the preview-side rendering rules for AsciiDoc and Markdown output.
The 24 `--skr-*` CSS custom properties live at `:root` with Catppuccin Mocha values. Theme overrides come from JavaScript via inline style on `:root`.

== IPC pattern

Frontend → Rust: `invoke<ReturnType>('command_name', args)`.
The `#[tauri::command]` annotation on the Rust side exposes a function as a callable command.
Args are JSON-serialized. Return values are JSON-deserialized.

Rust → Frontend: events, via `app.emit('event-name', payload)` on the Rust side and `listen<PayloadType>('event-name', handler)` on the JS side.
Used for OS-dispatched file opens (`skrivro:open-file`).

Capabilities are declared in `src-tauri/capabilities/default.json`: the Tauri permission system gates which commands and plugin features the frontend can actually invoke.
This is a CSP-adjacent security boundary: even if the frontend code tries to call something not in the capability list, the runtime blocks it.

== State and storage

Skrivro keeps four kinds of state, in different places for different reasons:

[cols="1,2,3", options="header"]
|===
| Kind | Where | Why there

| User config (`skrivro.conf`)
| Platform config dir (`~/.config/com.skrivro.editor/` on Linux, etc.)
| Conventional location, follows OS guidelines, easy to back up.

| UI prefs (`prefs.*` keys)
| WebView localStorage
| Per-machine UI state: display mode, Vim toggle, top bar visibility. Doesn't make sense to share across devices.

| Session state (last-opened file, window state)
| Platform data dir (`~/.local/share/com.skrivro.editor/` on Linux, etc.)
| Smaller-grain than config. Distinguished by being app-managed, not user-edited.

| Autosave draft
| WebView localStorage
| Crash recovery: needs to be written every 500ms during edits, which would be excessive disk I/O if it went to a real file. localStorage is debounced by the browser internally and survives a webview crash.
|===

== Build pipeline

`vp run tauri build` orchestrates two builds in sequence:

1. *Vite+ frontend build.* Reads `src/main.ts` as the entry, resolves all imports, transpiles TypeScript, bundles into `dist/index.html` + `dist/assets/*.js` + `dist/assets/*.css`. Vite+ is configured via `vite.config.js`.
2. *Cargo Rust build.* Compiles `src-tauri/` in release mode, statically linking where possible. Tauri's build script (`build.rs` calls `tauri_build::build()`) generates code that embeds the `dist/` directory into the binary.

The result is a single binary that contains both the Rust code and the bundled frontend.
Tauri's bundler (the third stage) wraps it in platform-appropriate installers on macOS (DMG) and Windows (MSI/NSIS), while the Linux artifact is the raw binary.

`vp run tauri dev` swaps step 1 for `vp dev` (a hot-reload dev server) and runs the Rust binary in debug mode pointed at that server instead of the bundled assets.

== Design choices worth knowing

=== One file per Rust concern, except Rust

The Rust side (`lib.rs`) is monolithic. The frontend (`src/`) is split by feature.
That asymmetry is deliberate: frontend code touches the DOM, Vim plugin, CodeMirror compartments, and other moving parts that benefit from explicit module boundaries.
The Rust code is mostly straight-line: parse a config, expose some commands, build a window, run.
Splitting it would add `mod` plumbing without separating any genuinely independent concerns.

=== Live bindings, not getters

Several modules export live bindings (`editorView`, `userConfig`, `currentBuffer`) that are reassigned at init time.
Importers see the reassignment automatically.
This is the standard ESM pattern for "this gets populated later", and it is cleaner than getter functions that thread the same state through the call graph.

=== Single-pane render is the default

Both panes render in every display mode, even when one is hidden.
When the editor pane is hidden (preview-only mode), `setDisplayMode` blurs the editor's `contentDOM` to keep CM6's focus state coherent with the visual state.
Without this, keystrokes in preview-only mode could end up routed to the hidden editor and silently appended to the document.

=== The status bar is dumb on purpose

`ui.ts`'s status-bar functions are pull-based: `refreshStatus` is called at every selection change, mode change, render, and so on, and each call rebuilds the status bar's content from current state.
There's no event subscription system, no reactive bindings.
For the small number of fields shown and the low rate of updates, the simpler approach is also the easier-to-debug one.

=== TypeScript strict mode

The frontend is full TypeScript strict mode (`strict: true`, `noImplicitAny`, `strictNullChecks`, `useUnknownInCatchVariables`, etc.).
There are a few `any` casts at external-library boundaries (`@replit/codemirror-vim` doesn't ship usable types, and `@asciidoctor/core`'s own types use `any` in places we don't try to over-tighten).
Each is documented at the cast site.

=== Themes are CSS custom properties at `:root`

Theme application is JavaScript writing `:root` inline styles, not switching stylesheets or using `<link>` swaps.
The CSS uses `var(--skr-*)` everywhere, falling back to compiled-in Catppuccin Mocha defaults if a slot isn't overridden.
A theme file's parsed values become inline style declarations on `:root`, which take precedence via specificity.
